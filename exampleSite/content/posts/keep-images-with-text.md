写博客的人迟早会面对一个问题：图片放哪。

默认答案是图床。传上去，拿一个链接，粘进 markdown。省事，而且看起来天经地义——毕竟「网站要放图，图总要有个地方」。我试过，后来全搬回来了。

## 图床坏在哪

不是速度，也不是费用，是**它把一篇文章拆成了两个东西**。

正文在你的仓库里，受版本控制，可以 diff、可以回滚、可以整站克隆下来就跑。图片在别人的服务器上，不受任何约束。于是：

- 图床改域名，你文章里的图全挂——而且是在你毫不知情的时候
- 图床停止服务，你的旧文章就变成一堆裂图
- 你想把站迁走，得先把几百张图一张张下回来
- 你在本地写文章，网络不通时预览不了自己的图

这些都是「图不在你手里」的直接后果。付费图床也一样，只是把风险推远了一点。

## 放旁边就好了

Hugo 的 **page bundle** 给了个很自然的解法：一篇文章连它的图片，放进同一个文件夹。

```
content/posts/my-post/
├── index.md
└── photo.jpg
```

正文里写 `![说明](photo.jpg)`，就完了。构建时自动压缩、转 WebP、生成响应式 srcset、加懒加载。

好处不只是省事：

- **本地所见即所得**——图片在磁盘上，网断了照样预览
- **搬站是一次 `git clone`**，不是一次数据迁移
- **图片和正文一起进版本**，改图、换图、回滚都在同一条时间线上
- 构建产物可以整站镜像，因为所有东西都在源头

代价是仓库体积会涨。但对一个博客来说，正文配图的量级完全撑得住。

## 唯一的例外

视频、音频这类大文件另说——它们不适合进 Git 历史，放对象存储更合适。所以主题里管自托管媒体的三个短代码，路径既认站内文件，也认 `http(s)://` 外链。

除此之外，**图和文章不该分家**。
